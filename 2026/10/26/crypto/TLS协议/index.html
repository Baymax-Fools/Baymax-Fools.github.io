TLS协议

TLS

注：TLS 工作在传输层之上（OSI模型的表示层），为上层应用提供机密性、完整性与身份鉴别，是 HTTPS 的安全底座。:D

TLS 是什么：从原语到协议

密码学原语（primitive）是积木：AES、RSA、SHA256、X25519……每一块单独看都很安全，但用户要的不是积木，是房子——两台素不相识的机器在不可信的网络上传数据，怎么协商出密钥、怎么确认对面不是骗子、怎么保证数据没被改？把积木按规定的流程拼起来，就是密码协议（protocol）。

TLS 的设计目标可以用 CIA 三性概括，每一条都能对应到协议里的具体机制：

性质 含义 TLS 里的对应
Confidentiality 机密 内容只有通信双方能看 握手协商出的对称密钥 + AEAD 加密
Authenticity 认证 对面确实是它声称的那个人 证书 + CA 签名 + CertificateVerify
Integrity 完整 数据在路上没被篡改 记录层 MAC/AEAD 标签 + Finished 校验

但只看安全是拼不出真实互联网的。从老年机到数据中心都在跑 TLS，于是有三个工程目标和 CIA 并列：互操作（实现不同、算法集不同也要能握手）、可扩展（新功能靠 extension 塞，不动核心协议）、高效（低端设备上密码运算很贵）。互操作和安全是天然打架的——正为了让古董设备也能连，才有服务器到今天还留着 TLS 1.0 甚至 SSL 3.0 的口子，而这些版本早就破得筛子一样（POODLE 等）。协议设计里一半的别扭都来自这个拉扯。

一次 HTTPS 连接的完整解剖（明文视角）

在浏览器里敲下一个 https:// 网址回车，网络上实际发生的事，按顺序是八幕。拿 Wireshark 抓一次自己浏览器的访问对着看最直观（一次典型抓包的前 50 个包大致就是这出戏）：

包区间 幕 明文吗
1–4 抓包背景噪声 —
5–6 DNS：问目标域名的 IP 全明文
7–9 TCP 三次握手，连服务器的 443 端口 头明文
10–11 ClientHello：客户端亮出支持的全部参数 明文（这就是它的使命）
12–17 ServerHello + ChangeCipherSpec + ApplicationData：服务器应答，然后——注意——连证书都是密文（TLS 1.3 特色） 半明文半密文
18–21 OCSP：查证书有没有被吊销 明文
22–27 客户端 CCS + 第一个 HTTP 请求（已加密） 密文
28–39 HTTP 响应到达 密文
40–50 页面里的 CDN 域名再做一轮 DNS 全明文

几个值得咂摸的细节：

  • 传统 DNS 是明文的——你在访问什么网站，围观者看得一清二楚，这是 DoH（DNS over HTTPS）这几年的动机；
  • TLS 记录的外层头永远是明文的（协议类型、长度藏不了，见下一节），但 ServerHello 之后的所有握手内容在 1.3 里全部进密文；
  • OCSP 单独跑在 HTTP 上查证书吊销状态，也是明文围观点。

Wireshark 三个实用技能：View → Resolution → Resolve Network Addresses 把 IP 解析成域名（私网地址要手动标）、右键字段 Apply as Filter、以及直接在过滤栏写表达式——比如数一数有多少包是发给目标服务器的：ip.dst == <服务器IP>，过滤栏会直接给出包数。

记录层：一切数据的信封

TLS 不直接发消息，所有数据（包括握手本身）都切成不超过 16KB 的块，套进记录层（record layer）的信封里：

信封皮是明文的——type 和长度暴露是设计上的坦荡（流量分析本来就防不了），但内容全在 payload 里加密。TLS 1.3 还嫌握手期太显眼：ServerHello 之后的握手消息外面统一套 type=23（ApplicationData）的皮，围观者连”这是证书还是密钥交换”都分不出来。

ClientHello / ServerHello：互亮底牌

握手第一步，双方各自报家门。ClientHello 的关键字段：

字段 内容 备注
legacy_version 客户端希望的最高版本 真实协商走 supported_versions 扩展
random 32 字节新鲜随机数 进密钥派生 + 防重放，人手一个
legacy_session_id 会话恢复用 1.2 时代的复活卡
cipher_suites 客户端支持的套件列表 按优先级排序，全亮出来
legacy_compression_methods 压缩方法 基本只剩 null（CRIME 攻击杀死了压缩）
extensions 扩展列表 SNI（要访问哪个域名）、key_share（1.3 的 DH 公钥）、signature_algorithms、ALPN……

ServerHello 逐项回拍：从套件列表里选一个、给出自己的 32 字节 Random、（1.3）回自己的 key_share 公钥。双方从这一刻起就有了共同的原料：两个 Random + 选定的算法 + DH 共享密钥。

两个 Random 的双重身份值得单独记：它们既是握手新鲜度的保证（防重放），又直接作为密钥派生的输入（master_secret 公式里能看到它们）——协议设计里”一个字段干两件事”的节俭美学。

密码套件：一串名字四件事

ServerHello 选定的那个”套件”（cipher suite）决定接下来整条连接用什么算法。以 OpenSSL 风格命名解剖：

IANA 官方写法是 TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256，一个意思。四个坑位依次回答四个问题：怎么换密钥、怎么验身份、怎么加密、怎么保完整。

两个易混点：

  • 第二段（RSA）指证书公钥用来签名认证，不是用来加密数据——看到 ECDHE-RSA 就该反应过来”RSA 密钥交换 + RSA 认证”两码事，Bare RSA 套件（TLS_RSA_WITH_*）里 RSA 才是真·密钥交换，那是下一个坑位的故事；
  • TLS 1.3 的套件名突然变短：TLS_AES_128_GCM_SHA256 只剩两段——因为 1.3 把密钥交换算法从套件里拆走了（全员 (EC)DHE/PSK，靠 key_share/psk 扩展协商），认证算法也不再看套件脸色。套件名瘦身本身就是版本演进的路标。

证书与 CA：信任的链条

对称密钥好办，难的是开头那句”对面确实是它声称的那个人”。如果我连咖啡店 WiFi 都不敢信，那 ServerHello 里自称某域名的公钥凭什么信？

答案是证书（certificate）：服务器公钥 + 域名身份，由 CA（Certificate Authority，证书颁发机构）用私钥签名背书。而 CA 的公钥又由更上一级 CA 签名……一路签到一个预装在你操作系统/浏览器里的根 CA。验证证书就是沿着这条链爬到根——根是信任的起点，全网一共百来个，都是过审的商业机构（DigiCert、Sectigo 这类）。

配套的运维问题：私钥泄露了怎么办？证书有有效期，紧急作废靠吊销机制——CRL（定期发的吊销清单）和 OCSP（在线实时查，就是解剖表里 18–21 包那段）。双向认证场景（mTLS）里客户端也掏证书，服务端同样验链——企业内网 API 常这么玩。

证书的坑很多（弱签名算法、链校验漏洞、CT 日志……），留待以后细讲。先立住主干：证书 = 身份+公钥的 CA 背书，链爬到根为止。

密钥交换：从 RSA 到 (EC)DHE

终于到 TLS 的灵魂问题：双方怎么在明文信道上商量出一个窃听者拿不到的密钥？

方案一：RSA 密钥交换（TLS 1.2 遗产，正在退场）

简单直接，但有宗罪：没有前向保密（forward secrecy）。攻击者今天把密文全录下来存着——假设十年后拿到了服务器私钥（泄露、下线、被黑），历史流量全部解开。情报机构就是这么干的：录了再说，钥匙慢慢等。这叫”先存后解”（store now, decrypt later）。

方案二：临时 DH（(E)phemeral (EC)DHE，现役标准）

Diffie–Hellman 的魔力在于：双方各持一个临时私钥，公钥明文互换，各自算出同一个共享密钥——窃听者拿到全部交换报文也算不出来。关键是”临时”二字：这一对密钥用完即焚，会话结束私钥就删。哪怕日后服务器证书私钥泄露，录下来的流量里只有明文的 DH 公钥，往事依然是往事。前向保密的本质：会话密钥的安全不依赖任何长期秘密。

分工也就清晰了：证书密钥对只负责认证（签名证明”我是我”），从不碰会话密钥；会话密钥由临时 DH 一手包办。

TLS 1.3 的手术：直接删掉 ClientKeyExchange 消息和整个静态 RSA 交换，只留 (EC)DHE（和少量 PSK）；DH 公钥塞进 ClientHello 的 key_share 扩展里随首包一起发——握手从 2-RTT 砍到 1-RTT。顺带地，折腾了 RSA 密钥交换二十年的 Bleichenbacher 填塞预言机一族攻击（→ DROWN → ROBOT）物理失去宿主。1.3 的密钥派生也换了引擎：PRF 换成 HKDF 阶梯（Early → Handshake → Master 三级 Extract，每一级 Derive-Secret 都把当时的 transcript 哈希焊进密钥，详见 RFC 8446 §7.1）。

TLS 1.2 vs 1.3：一张表看清

TLS 1.2 TLS 1.3
证书传输 明文，围观者看得到服务器身份 密文（ServerHello 后全加密）
握手往返 2-RTT 1-RTT（PSK 恢复可 0-RTT）
密钥交换 RSA / 静态 DH / DHE / PSK 只剩 (EC)DHE / PSK，强制前向保密
ClientKeyExchange 有 删除（key_share 进 ClientHello）
对称加密 CBC / RC4 / AEAD 混杂 AEAD only
套件命名 四段式 ECDHE-RSA-AES128-GCM-SHA256 两段式 TLS_AES_128_GCM_SHA256
密钥派生 PRF（HMAC- SHA256/384） HKDF 阶梯 + transcript 绑定

证书加密这一条的现实冲击：企业网络安全设备（DLP、被动审计）过去靠读明文证书+私钥解密的”合法中间人”套路在 1.3 面前集体失效，只能转向终端装信任根的主动代理——这也是 RFC 系列文档 Industry Concerns about TLS 1.3 记录的那场攻防。

Finished：握手的最终裁决

握手四阶段：交换能力 → 验证身份 → 协商密钥 → 校验完整性。最后一步的主角是三个认证消息：

  • Certificate：证书链，身份的载体（mTLS 时客户端也发一份）；
  • CertificateVerify：服务器用证书私钥对到目前为止的整个握手签名——证明它真的持有证书对应的私钥，而不是转发别人的证书。TLS 1.2 的实现没把此前所有消息都盖进签名范围，是个被 1.3 修掉的弱点；
  • Finished：双向的最终校验。双方各发一个 verify_data，对全部握手消息做总签证。

verify_data 的算法（TLS 1.3，RFC 8446 §4.4.4）：

Transcript-Hash 把握手消息（不含记录层头）按线上字节序拼起来整体哈希。这个设计叫 transcript 绑定：密钥和校验值都是从”对话历史”派生的，中间人篡改任何一条消息——哪怕只是把客户端支持的套件列表改弱一点（降级攻击）——Finished 必然对不上，连接当场翻脸。

想检验自己理解到不到位，拿 RFC 8448（官方 Example Handshake Traces）逐字段对拍一次完整握手，是最硬的手段。

NSS Key Log Format

解密 TLS 流量的那把”钥匙”

NSS Key Log Format 最早由 Mozilla 的密码库 NSS 定义，如今是解密 TLS 流量的事实标准（de facto standard）——它并非任何 RFC 规定的官方协议，却几乎被整个生态采用。
格式本身非常简单：纯文本，每行三个空格分隔的字段 <标签> <ClientRandom> <密钥>。

  • 标签表明这是 TLS 密钥调度中派生出的哪一把 secret，如解密握手消息的 CLIENT/SERVER_HANDSHAKE_TRAFFIC_SECRET、解密应用数据的 CLIENT/SERVER_TRAFFIC_SECRET_0；
  • ClientRandom 是该会话 ClientHello 里的 32 字节随机数，相当于”会话身份证”，分析工具靠它把密钥匹配到 pcap 里的具体连接；
  • 最后一个字段才是真正的密钥材料（hex 编码的 HKDF 输出，TLS 1.3 中的SHA-384套件为 48 字节）。
  • 一个文件里可以同时存在多场会话的密钥，全靠 ClientRandom 区分。

这个文件的珍贵之处在于：TLS 1.3 强制 (EC)DHE 前向保密，即使拿到服务器 RSA 私钥也推不出会话密钥，keylog 是解密流量的唯一入口。

示例：

解密 TLS 流量的三条路

把协议看完，解密手里的一段 TLS 流量其实就三条路，按适用条件排列：

  1. RSA 私钥：只对静态 RSA 密钥交换的 TLS 1.2 流量有效；遇到 (EC)DHE 直接歇菜——这是”我明明有服务器私钥却解不开”的经典翻车原因；
  2. NSS Key Log：客户端主动导出的会话密钥，1.2/1.3 通吃，前向保密时代的唯一被动解密入口（即上一节的 keylog 文件）；
  3. 主动 MITM：终端装信任根，代理冒充服务器——1.3 时代企业监控的唯一出路，属于攻击者视角的玩法了。

Wireshark 的入口统一在 Preferences → Protocols → TLS：RSA 私钥填 Key File，keylog 填 (Pre)-Master-Secret log file。
