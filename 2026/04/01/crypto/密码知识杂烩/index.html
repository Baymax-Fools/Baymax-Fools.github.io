密码知识杂烩

消息认证码（MAC）

经过特定算法后产生的一小段信息，检查某段消息的完整性，作为身份验证，确认消息的来源
MAC的算法中，通常会使用带密钥的散列函数，或块密码的带认证工作模式

伽罗瓦消息认证码（GMAC）：是GCM的一种仅用于认证的变体（明文为空、只认证附加数据），可以形成增量消息认证码。GCM和GMAC都可以接受任意长度的初始化向量，但推荐固定使用 96 位——其他长度的 IV 需要先用 GHASH 推导 J0，属于 GCM 实现 bug 的高发区

GCM工作模式

GCM 全称为 Galois/Counter Mode：G 指 Galois（认证标签在伽罗瓦域 GF(2^128) 上计算，即 GMAC），C 指 CTR。它在 CTR 加密的基础上增加 GMAC 的特性，解决了 CTR 不能对加密消息进行完整性校验的问题。

加密（输入：密钥 K、明文 P、初始向量 IV、附加数据 AD）：

  1. 用密钥对明文加密得到 C
  2. 用密文和 AD 计算得到认证标签 T

解密：

  1. 接收者（持有密钥 K）接收到 AD、C、T
  2. 正常解密出 P
  3. 重算并校验 T，检查密文或 AD 是否被篡改

GCM 内部细节（NIST SP 800-38D）

  • 哈希子密钥 H = E_K(0^128)，认证运算在伽罗瓦域 GF(2^128) 上进行（GHASH）
  • 96 位 IV 时 J0 = IV || 0^31 || 1；其他长度的 IV 要先用 GHASH 推导 J0
  • 加密：C 由从 inc32(J0) 起算的 CTR 模式生成（第一个计数器块是 J0+1）
  • 标签：T = MSB_t(GHASH_H(AD, C) ⊕ E_K(J0))，GHASH 依序处理 AD、密文和长度块 [len(AD)]64 || [len(C)]64
  • IV 唯一性是安全前提：同一 IV 重用会泄露 H（进而可伪造任意消息的标签），同时 CTR 密钥流重用会直接泄露两段明文的异或

信封加密（混合加密）

非对称加密慢但解决了密钥分发，对称加密快但密钥怎么送是个问题——混合加密两者兼得：用对称的会话密钥加密数据，再用接收方公钥加密这个会话密钥，两者打包即为“信封”。

  • 学术上常拆成 KEM（密钥封装）+ DEM（数据封装）两块；现代构造如 ECIES、HPKE（RFC 9180）
  • 云厂商语境下的“信封加密”：数据密钥 DEK 加密数据，主密钥 KEK 加密 DEK，KEK 托管在 KMS 不落业务侧
  • CTF 常见形态：RSA/EC 加密的会话密钥 + AES 密文，先攻前半段拿到会话密钥再解密文

口令

口令（password）和密钥的本质差异是熵：人类口令通常只有几十 bit 熵，扛不住离线枚举，所以口令的存储/派生必须用专门的慢函数（KDF）：

  • PBKDF2：迭代次数可调，但没有内存硬度，GPU/ASIC 枚举效率高
  • bcrypt / scrypt：scrypt 引入内存参数
  • Argon2id（Password Hashing Competition 优胜）：时间、内存双参数可调，当前首选

口令熵不够时 KDF 只是延缓而非阻止——弱口令配 Argon2 照样能被字典攻击磨出来。

带盐值的哈希函数

盐（salt）是随口令随机生成、和哈希一起存储的公开值，让相同口令得到不同哈希，彩虹表（预计算的 口令→哈希 对照表）因此失效：

  • 盐应当每用户随机（≥16 字节），不能全局共用一个
  • pepper（服务端秘密，不进数据库）可再加一层：数据库被拖走也差最后一把钥匙
  • 常见死法：无盐 MD5/SHA1 直接存口令，彩虹表秒查

与「口令」一节配套：盐解决“相同输入得到相同哈希”，KDF 解决“算得太快”，缺一不可。

HFE

HFE（Hidden Field Equations，Patarin 1996）是多变量公钥密码的代表：在扩域 GF(q^n) 上取一个易求逆的中心映射（次数受限制的多项式），再用可逆仿射映射 S、T 把真实变量“藏”起来，公钥即复合后的多变量二次方程组。

  • 私钥 = 中心映射 + 仿射映射；解密/签名就是反向走一遍
  • 经典攻击（Patarin、Kipnis–Shamir）：从公钥方程组诱导出扩域上的低次/线性关系，还原隐藏结构，基础 HFE 已不安全
  • 加固变体 HFEv-（如 GeMSS，曾进入 NIST 后量子签名标准化第三轮备选）：加扰动项与醋变量

UOV（不平衡油醋签名）

油醋签名（Oil and Vinegar，Patarin 1997）：方程组中分“油变量”和“醋变量”，油-油之间不出现乘积项，掌握油变量角色即可高效解方程完成签名；攻击者不知道谁是油谁是醋。

  • 平衡油醋（v = m）被 Kipnis–Shamir 攻破，此后只用“不平衡”参数（v > m），具体配比需对照最新攻击复杂度选取
  • 分层油醋即 Rainbow——2022 年被 Beullens 攻破（利用的是层间结构，不等价于 UOV 被破）
  • UOV 目前是 NIST 后量子附加签名标准化进程中的领先候选之一

与 HFE 同属多变量公钥密码：HFE 藏的是中心映射的结构，UOV 藏的是变量的角色。

JWT

使用会话 ID Cookie 时，会话信息存储在服务器上；而使用 JWT 时，会话信息则存储在客户端上。

HTTP 头部中用于向服务器发送 JWT 的字段名称：Authorization

示例：

JWT 由 Header.Payload.Signature 三段组成（均为 base64url 编码，可直接解开查看，payload 不是加密，别放敏感信息）。

JWT 常见攻击面

  • alg: none：服务端若接受无签名算法，可任意篡改 payload
  • 弱 HMAC 密钥（HS256）：jwt2john / hashcat 直接爆破
  • RS256 → HS256 混淆：服务端拿 RSA 公钥当 HMAC 密钥验签，攻击者用公开公钥即可伪造令牌
  • exp / nbf 未校验：过期令牌复活
  • kid / jku / x5u 字段注入：SQL 注入、路径穿越、指向攻击者 JWKS 的 SSRF

SSH 公钥认证

最典型的签名认证流程。口令认证证明“你知道一个秘密”，公钥认证证明“你持有私钥”——秘密从头到尾不上网，上网的只有一次对挑战的签名：

  1. 建连先做算法协商和 DH 密钥交换，得到会话密钥和全程唯一的 session_id；同时核对服务端 host key 指纹（记在 known_hosts 里，第一次连接没有记录会提示是否信任，即 TOFU：trust on first use）
  2. 客户端发起 publickey 认证，把用户名、签名算法、公钥发给服务端
  3. 服务端查 authorized_keys，有这个公钥就回复“请签名”
  4. 客户端用私钥对 session_id 和本次认证请求签名，发回
  5. 服务端用公钥验签，通过即登录；认证流量本身也走步骤 1 协商出的加密通道

几个关键点：

  • 签名绑定 session_id，换一条连接签名就作废——挑战-响应防重放的标准做法
  • 两个文件各管一边：服务端的 authorized_keys 决定“谁能登录我”，客户端的 known_hosts 决定“我在跟谁说话”。不先验 host key 就做认证，中间人两头通吃
  • 私钥文件本身用口令 + KDF 加密保存（OpenSSH 私钥格式用 bcrypt），偷到 id_rsa 还得先磨出口令——回到「口令」一节：KDF 只是延缓，弱口令照样磨得出来
  • ssh-agent：私钥常驻 agent 进程，签名请求转发给它完成，私钥不落盘不进 SSH 进程；ssh -A 把 agent 转发到跳板机 = 把签名权也借给了跳板机，跳板失守即可冒充你横向移动

SSH 常见攻击面

  • TOFU：第一次连接就被 MITM 的话，之后的一切信任都建立在被劫持的起点上（StrictHostKeyChecking 只能收紧首次行为）
  • CVE-2018-15473：OpenSSH ≤ 7.7 用户名枚举——公钥认证的计时差异暴露“这个用户存不存在、有没有配公钥”
  • Terrapin（CVE-2023-48795）：前缀截断——瞬时中间人重置序列号，把握手开头的扩展协商报文截掉实现降级，修复靠 strict KEX 严格同步序列号
  • agent 转发滥用：高权限跳板机上转发的 agent socket 谁都能用（root 直接拿 SSH_AUTH_SOCK 借签名），非必要不开 -A

ChaCha20-Poly1305

与 GCM 同级的 AEAD：ChaCha20 流密码负责加密，Poly1305 负责认证（每条消息的 Poly1305 一次性密钥由 ChaCha20 按 nonce 派生），IETF 版本（RFC 8439）nonce 96 位、tag 128 位。

  • 对比 AES-GCM：无 AES 硬件加速的平台上更快，纯软件实现天然常量时间，不易受时序侧信道影响
  • 应用：TLS 1.3、WireGuard、Noise 协议框架
